# AxonScope Solver Review — GPU Batching, Extracellular Modeling, MRG, and Pseudo-MRG

## 1. Executive Summary

The current solver architecture is a good starting point for single-axon simulations in JAX, but it is not yet ideal for the final target: **large-scale GPU batched simulations**.

The main issue is not the membrane model itself. The main issue is the current extracellular formulation:

- it solves a coupled `Vi / Ve` system;
- it builds `(Nx, 2, 2)` block matrices inside the time loop;
- it uses a custom block-tridiagonal Thomas solver;
- it repeats this solve multiple times per time step;
- it is structured around Python `axon` objects and closures rather than batchable arrays.

The best long-term direction is to separate:

```text
Vstim = externally imposed stimulation field, precomputed from electrodes
Vperi = dynamic periaxonal / extracellular-local potential for double-cable models
Vm    = membrane voltage, usually Vi - Vperi
```

This separation allows three solver levels:

```text
1. SingleCable
   Fast, simple, GPU-batch friendly.

2. PseudoMRGSingleCable
   Reduced MRG-like model, still single-cable and batchable.

3. FullMRGDoubleCable
   Accurate reference model, slower, used for validation and calibration.
```

---

## 2. Current Code Structure

The current code is already written with JAX in mind. The solvers operate on JAX arrays, use `jax.lax.scan` over time, avoid Python-side mutation, and are intended to be GPU-ready.

The code also already mentions future TODOs that directly match the present discussion:

- chunk simulation;
- batching capabilities;
- on-the-fly processing;
- saving methods with filtering;
- batching and post-processing support.

The base solver API currently describes a classic single-cable equation:

```text
dV/dt = D * d²V/dx² + (I_inj(t) - I_ion(V, gates)) / Cm
```

and returns a full simulation result containing voltage traces over time.

This is fine for single-axon simulations, but for GPU batch simulation it becomes problematic if the output is:

```text
V_all: [B, Nt, Nx]
```

because memory can dominate performance.

---

## 3. Current Extracellular Path

The current extracellular solver uses a generic `Vi / Ve` integration path. It initializes:

```text
Vm
Ve
Vi
gates
membrane state
diffusion coefficients
compartment areas
extracellular absolute arrays
```

including quantities such as:

```text
Cm_abs
Cx_abs
Gx_abs
Gax_e
```

Inside each time step, the solver computes:

```text
Vm_old = Vi_old - Ve_old
Iinj_abs = inj_fun(t_mid) * area
Vext = vext_fun(t_mid)
```

Then it builds a coupled block system for `Vi_new` and `Ve_new`. The block matrices are allocated as:

```python
A_diag  = zeros((Nx, 2, 2))
A_lower = zeros((Nx, 2, 2))
A_upper = zeros((Nx, 2, 2))
rhs     = zeros((Nx, 2))
```

and then passed to a custom `solve_block_tridiagonal_2x2`.

The coupling iteration is hardcoded to three internal iterations per time step:

```python
jax.lax.fori_loop(0, 3, iter_body, ...)
```

so the extracellular path performs three block-tridiagonal solves per time step.

This is the main performance concern.

---

## 4. Why the Current Extracellular Solver Is Not Ideal for GPU Batch

The custom `solve_block_tridiagonal_2x2` is algorithmically `O(Nx)`, which is good asymptotically. However, it performs a forward pass followed by a backward pass along the spatial axis. This creates a sequential dependency chain in `Nx`.

That is not ideal for GPUs.

For one axon:

```text
GPU parallelism over Nx is limited by the sequential Thomas-style solve.
```

For many axons:

```text
GPU parallelism comes mainly from the batch dimension B.
```

So the method can still work on GPU if `B` is large enough, but it will likely underuse the GPU for small or moderate batch sizes.

The current cost structure is roughly:

```text
Nt × 3 × block_tridiagonal_2x2(Nx)
```

For batch:

```text
B × Nt × 3 × block_tridiagonal_2x2(Nx)
```

The batch dimension helps, but the spatial solve remains sequential inside each batch element.

## 5. The Important Conceptual Split: `Vstim` vs `Vperi`

A key modeling clarification is needed.

The externally applied field from electrodes should not be conflated with the dynamic extracellular or periaxonal state of a double-cable model.

Recommended terminology:

```text
Vstim:
    Externally imposed potential field generated by electrodes.
    Fully precomputable.

Vperi:
    Dynamic local extracellular / periaxonal potential.
    Needed for full MRG-like double-cable models.

Vi:
    Intracellular potential.

Vm:
    Membrane voltage, usually Vm = Vi - Vperi.
```

In the current code, `vext_fun(t_mid)` provides an imposed field. That field enters the extracellular equation through the RHS term involving `Vext`. The dynamic unknown `Ve` is separate and is solved as part of the coupled system.

This distinction is crucial for designing a batchable solver.

---

## 6. Precomputing the External Field

The external stimulation field is fully precomputable.

Conceptually, for one electrode/context:

```text
Vstim(t, x) = I(t) * footprint(x)
```

For multiple electrodes:

```text
Vstim(t, x) = sum_e I_e(t) * footprint_e(x)
```

For GPU batch, the better representation is fully tensorized:

```python
Vstim:     [B, Nt, Nx]
# or
footprint: [B, E, Nx]
stim:      [B, E, Nt]
mask:      [B, E]
```

Then:

```python
Vstim[:, n, :] = sum_E(mask[:, E] * stim[:, E, n] * footprint[:, E, :])
```

The current implementation uses Python tuples of contexts and closures. That is elegant for one axon, but not ideal for GPU batching.

For large batch GPU simulation, prefer:

```python
Vstim_n = Vstim[:, n, :]
```

inside the solver scan.

## 7. Recommended Solver Family

The cleanest architecture is not one universal solver. It is a small hierarchy of solvers with different accuracy/performance tradeoffs.

```text
SingleCableKernel
    Fastest.
    No dynamic Vperi.
    Uses precomputed Vstim or forcing.

PseudoMRGSingleCableKernel
    Reduced MRG-like model.
    Keeps MRG-like geometry and effective parameters.
    Does not solve the full double cable.

FullMRGDoubleCableKernel
    Accurate reference model.
    Solves Vi and Vperi dynamically.
    Used for validation, calibration, and smaller batches.
```

---

## 8. Single-Cable Reformulation with Precomputed Extracellular Forcing

For fibers that do not require a dynamic periaxonal potential, do not solve `Ve`.

Instead, treat the extracellular field as an imposed field:

```text
Ve(x, t) = Vstim(x, t)
```

Then:

```text
Vi = Vm + Vstim
```

The axial term becomes:

```text
L(Vi) = L(Vm + Vstim)
      = L(Vm) + L(Vstim)
```

So the stimulation enters the membrane equation as a known forcing term.

The resulting solve is scalar:

```text
Vm_new = scalar_tridiagonal_solve(...)
```

instead of:

```text
[Vi_new, Vperi_new] = block_tridiagonal_2x2_solve(...)
```

This is the most GPU-batch-friendly path.

Recommended tensor shape:

```python
Vm:       [B, Nx]
gates:    [B, Nx, Ng]
Vstim:    [B, Nt, Nx]
forcing:  [B, Nt, Nx]  # optional precomputed L(Vstim)
```

The forcing can be computed once before the simulation if memory allows.

## 9. Full MRG / Double-Cable Path

For MRG-like models, you do need a dynamic extracellular/periaxonal state.

In that case, the correct conceptual model is:

```text
Vstim -> imposed external bath/electrode field
Vperi -> dynamic local extracellular/periaxonal potential
Vi    -> intracellular potential
Vm    -> Vi - Vperi
```

The full double-cable model should keep the coupled system, but it should be rewritten for batch.

Instead of generic block matrices:

```python
A_diag:  [B, Nx, 2, 2]
A_lower: [B, Nx, 2, 2]
A_upper: [B, Nx, 2, 2]
```

prefer scalar coefficient arrays:

```python
a00:  [B, Nx]
a01:  [B, Nx]
a10:  [B, Nx]
a11:  [B, Nx]

li:   [B, Nx-1]  # intracellular axial coupling
le:   [B, Nx-1]  # extracellular/periaxonal axial coupling

rhs0: [B, Nx]
rhs1: [B, Nx]
```

The block structure is simple enough that a specialized solver will be faster and easier to batch.

## 10. Pseudo-MRG: Reducing Double Cable to Single Cable

A “pseudo-MRG” model is a very good idea for large GPU batches.

The goal is to approximate the effects of the MRG double cable without solving `Vperi` as a full dynamic cable.

The reduced model would keep:

```text
Vm
gates
MRG-like compartment structure
effective nodal/internodal parameters
precomputed Vstim
```

but remove:

```text
full dynamic Vperi cable solve
2x2 block-tridiagonal system
```

This gives a single-cable model with effective parameters:

```text
Cm_eff(x)
Gleak_eff(x)
D_eff(x)
alpha_ext(x)
tau_ext(x)        optional
beta_feedback(x)  optional
```

---

## 11. Possible Pseudo-MRG Variants

### 11.1 Simple Field-Filtered Pseudo-MRG

Approximate:

```text
Vperi(x, t) ≈ alpha(x) * Vstim(x, t)
```

or with a local first-order filter:

```text
tau(x) dZ/dt = alpha(x) Vstim(x, t) - Z
Vperi ≈ Z
```

This is extremely batchable.

Pros:

```text
Very fast.
No spatial double-cable solve.
Easy to implement.
```

Cons:

```text
No feedback from membrane current to periaxonal voltage.
May miss important MRG dynamics during spikes.
```

---

### 11.2 Effective-Admittance Pseudo-MRG

Absorb the double-cable effect into effective single-cable parameters:

```text
Cm_eff
Gm_eff
D_eff
Istim_eff
```

This is probably the best reduced model for production.

The single-cable equation becomes:

```text
Cm_eff dVm/dt =
    axial_eff(Vm)
    - Iion(Vm, gates)
    + Istim_eff(Vstim)
```

Pros:

```text
Fast.
Batchable.
Still biophysically interpretable.
Can be fitted against full MRG.
```

Cons:

```text
Requires calibration.
May be stimulus-regime dependent.
```

---

### 11.3 Quasi-Static Elimination of `Vperi`

Assume the periaxonal space equilibrates quickly:

```text
dVperi/dt ≈ 0
```

Then approximate:

```text
Vperi_i ≈ beta_i * Vm_i + alpha_i * Vstim_i
```

or with local neighbor information:

```text
Vperi_i ≈ beta_i * Vm_i
        + alpha_i * Vstim_i
        + gamma_i * local_smooth(Vstim)_i
```

Pros:

```text
Closer to the double-cable equations.
Can include membrane-to-periaxonal feedback.
```

Cons:

```text
Exact elimination is nonlocal if Gax_e is retained.
A local approximation must be validated carefully.
```

## 12. Recommended Data Model for GPU Batch

Avoid passing Python `axon` objects into the JAX kernel.

Instead, use a two-stage design:

```text
Python preparation:
    Axon objects -> static arrays / padded batch tensors

JAX kernel:
    arrays -> simulation
```

Example structures:

```python
@dataclass
class StimulusBatch:
    Vstim: jnp.ndarray       # [B, Nt, Nx]
    forcing: jnp.ndarray     # [B, Nt, Nx], optional


@dataclass
class SingleCableBatchParams:
    lower: jnp.ndarray       # [B, Nx]
    diag: jnp.ndarray        # [B, Nx]
    upper: jnp.ndarray       # [B, Nx]
    Cm: jnp.ndarray          # [B, Nx]
    area: jnp.ndarray        # [B, Nx]


@dataclass
class DoubleCableBatchParams:
    Cm_abs: jnp.ndarray      # [B, Nx]
    Cx_abs: jnp.ndarray      # [B, Nx]
    Gx_abs: jnp.ndarray      # [B, Nx]
    Gax_i: jnp.ndarray       # [B, Nx-1]
    Gax_e: jnp.ndarray       # [B, Nx-1]
    area: jnp.ndarray        # [B, Nx]
```

If axons have variable `Nx`, use padding and masks:

```python
valid_compartment_mask: [B, Nx_max]
```

If axons have variable numbers of electrodes:

```python
footprints: [B, Emax, Nx]
stim:       [B, Emax, Nt]
ctx_mask:   [B, Emax]
```

## 13. Output Strategy

For GPU batch, avoid always returning the full voltage trace:

```text
V_all: [B, Nt, Nx]
```

This can become enormous.

Recommended output modes:

```text
full_trace:
    Return all Vm values.
    Useful for debugging and small batches.

probes:
    Return Vm at selected compartments only.

final_state:
    Return final Vm, gates, and internal states.

features:
    Return spike count, threshold crossing, latency, max Vm, etc.

chunked:
    Simulate in temporal chunks and stream/reduce outputs.
```

## 14. Performance Priorities

### Priority 1 — Precompute `Vstim`

Since the external field is fully precomputable, remove stimulus interpolation and context summation from the inner time loop whenever possible.

For GPU batch, prefer:

```python
Vstim_n = Vstim[:, n, :]
```

---

### Priority 2 — Avoid the Full Double-Cable Path Unless Needed

Only use dynamic `Vperi` for fibers that truly require it.

```text
SingleCable:
    no Vperi solve

PseudoMRG:
    reduced Vperi effect

FullMRG:
    dynamic Vperi solve
```

---

### Priority 3 — Specialize the Block Solver

For full MRG, replace generic `(Nx, 2, 2)` matrices with scalar coefficient arrays.

A specialized batched solver should operate directly on:

```python
a00, a01, a10, a11
li, le
rhs0, rhs1
```

---

### Priority 4 — Make Coupling Iterations Configurable

The current extracellular generic path uses three fixed internal iterations.

Expose:

```python
n_coupling_iter = 1 | 2 | 3
```

Then benchmark accuracy vs runtime.

---

### Priority 5 — Separate Validated and Experimental Solvers

Keep:

```text
FullMRGDoubleCableReference
```

as a validation target, and make faster reduced solvers explicitly approximate.

---

## 15. Validation Plan

The pseudo-MRG should not be judged by whether it reproduces `Vperi` exactly. It should be judged by whether it reproduces useful outputs.

Compare against full MRG on:

```text
activation threshold
rheobase / chronaxie
latency
conduction velocity
nodal AP waveform
threshold-distance curves
response to pulse width
cathodic vs anodic stimulation
multi-electrode stimulation
```

Suggested workflow:

```text
1. Run FullMRGDoubleCable on a representative parameter set.
2. Generate training/validation data.
3. Fit PseudoMRG parameters.
4. Validate on unseen stimulus amplitudes, pulse widths, and electrode distances.
5. Use PseudoMRG for large GPU screening.
6. Recheck selected cases with FullMRG.
```

## 16. Proposed Final Architecture

```text
axonscope/
  solvers/
    kernels/
      single_cable_batch.py
      pseudo_mrg_batch.py
      full_mrg_double_cable_batch.py

    reductions/
      fit_pseudo_mrg.py
      validate_pseudo_mrg.py

    reference/
      full_double_cable_single_axon.py
```

Runtime flow:

```text
1. Build axon objects.
2. Compile/pad them into batch arrays.
3. Precompute Vstim.
4. Choose solver:
       SingleCable
       PseudoMRG
       FullMRG
5. Run JIT-compiled batch kernel.
6. Return probes/features/full trace depending on output mode.
```

## 17. Decision Matrix

| Model | Accuracy | GPU Batchability | Runtime | Use Case |
|---|---:|---:|---:|---|
| SingleCable + precomputed Vstim | Medium | Excellent | Fastest | Large screening, unmyelinated/simple fibers |
| PseudoMRGSingleCable | Medium-high if calibrated | Excellent | Fast | Large MRG-like screening |
| FullMRGDoubleCable, specialized batched block solver | High | Medium | Slower | Validation, smaller batches |
| Current generic extracellular solver | High-ish, depending on scheme | Low-medium | Slower | Prototype/reference, not ideal for production GPU batch |

---

## 18. Main Recommendation

The best design is not to force every fiber through the full extracellular `Vi / Ve` solver.

Instead:

```text
Use precomputed Vstim for all models.
Use dynamic Vperi only when the model truly requires it.
Use PseudoMRG for large-scale GPU batches.
Use FullMRGDoubleCable as the reference/calibration model.
```

In short:

```text
Vstim is input data.
Vperi is a model state.
Do not conflate them.
```

That separation gives a clean path toward scalable GPU batching while preserving a faithful full-MRG reference model.
