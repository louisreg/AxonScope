# Efficient Coupling of FEM Extracellular Fields with GPU-Ready 1D Axon Solvers

Status: future integration proposal. External geometry/FEM packages own field
solving, trajectories, point location, and projection. AxonFleet consumes only
the resulting sampled extracellular footprints. The active task and product
boundary are tracked in `todo.md` and `GUIDELINES.md`.

## 1. Context and Goal

This document describes an efficient architecture for a simulation package that models the effect of electrical stimulation on nerve fibers.

The overall workflow is:

1. Solve the quasi-static extracellular potential problem using a 3D FEM model of the electrode, surrounding tissue, and nerve.
2. Project the resulting extracellular potential onto many 1D axon trajectories.
3. Use a GPU-ready 1D axon solver to compute membrane dynamics, thresholds, activation, or recruitment.

The central performance concern is that the 1D axon solver may run efficiently on GPU, while the FEM solver and the FEM-to-axon projection may remain CPU-bound. For large axon populations, the projection step itself can become a bottleneck if implemented naively.

The goal is therefore not necessarily to make the FEM solver GPU-native immediately, but to design the coupling so that:

- FEM solves are reused as much as possible.
- Expensive geometric point-location is performed only once.
- Projection is represented as a reusable sparse operator.
- CPU-to-GPU transfers are minimized.
- Large populations can be processed by chunks or with fused GPU kernels.
- The architecture remains extensible to future GPU FEM backends.

---

## 2. High-Level Architecture

A recommended high-level pipeline is:

```text
3D FEM model: electrode + nerve + surrounding medium
        |
        | solve Poisson / quasi-static conduction problem
        v
Extracellular field basis Φ_k(x), one field per independent contact
        |
        | project/interpolate onto 1D axon trajectories
        v
Axonal field basis V_e,k(s), one projected field per contact
        |
        | combine with stimulation waveforms
        v
V_e(s, t) = Σ_k a_k(t) V_e,k(s)
        |
        | GPU-ready 1D axon solver
        v
spikes, thresholds, recruitment curves, activation maps
```

The important abstraction is that the FEM solver does not directly feed a single time-dependent axon simulation. Instead, it produces a **field basis** or **transfer basis** from electrodes to extracellular potentials along axons.

---

## 3. Exploiting Linearity of the FEM Problem

For many electrical stimulation models, the extracellular potential is obtained from the quasi-static equation:

```math
∇ · (σ ∇φ) = 0
```

where:

- `φ` is the extracellular potential,
- `σ` is the tissue conductivity tensor or scalar conductivity.

If the tissue conductivities, geometry, and boundary conditions are linear, then the solution is linear with respect to injected currents or electrode voltages.

Therefore, instead of solving a new FEM problem for every stimulation waveform or amplitude, solve a set of basis problems:

```math
Φ_k(x)
```

where `Φ_k` is the potential field generated by contact `k` under a normalized stimulation condition, for example:

- 1 mA injected through contact `k`,
- 1 V imposed on contact `k`,
- one active contact with a defined return electrode,
- or one independent electrode mode in a chosen stimulation basis.

Then the time-dependent extracellular potential is reconstructed as:

```math
φ(x, t) = Σ_k a_k(t) Φ_k(x)
```

where `a_k(t)` contains the waveform, amplitude, and contact weighting.

This means that, in many workflows, the FEM solve is a precomputation step rather than something that must be run inside every simulation loop.

## 4. FEM Solver Strategy

### 4.1 First Priority: Reuse and Cache

Before porting the FEM solve to GPU, the package should make the CPU FEM path efficient and reusable.

Recommended practices:

- Assemble the FEM matrix once when geometry and conductivities are fixed.
- Reuse the same matrix for multiple right-hand sides or electrode configurations when possible.
- Factorize or precondition once when feasible.
- Solve one basis field per independent electrode/contact mode.
- Store the resulting FEM field basis on disk.
- Include metadata to guarantee that cached fields are physically compatible with the current simulation.

A cached FEM result should include at least:

```text
FEMResult
  mesh identifier / mesh hash
  material properties
  conductivity model
  electrode configuration
  boundary-condition convention
  normalization convention
  potential reference convention
  nodal potential basis
  solver version
  units
```

### 4.2 When GPU FEM Becomes Worthwhile

GPU FEM becomes valuable if the workflow frequently changes:

- electrode geometry,
- electrode position,
- nerve geometry,
- tissue conductivities,
- mesh resolution,
- boundary conditions,
- or if inverse optimization requires many repeated FEM solves.

If the FEM geometry and conductivities are mostly fixed, a CPU FEM solver with caching may be sufficient. The larger performance opportunity is often in avoiding repeated projection and avoiding repeated CPU-GPU transfers.

## 5. The Projection Bottleneck

For large populations, the FEM-to-axon projection can become expensive if implemented as:

```text
for each axon:
    for each compartment:
        locate the containing FEM cell
        interpolate the FEM potential
        transfer the result to GPU
```

This is problematic because it repeats the most expensive geometric operation: finding which FEM cell contains each axonal compartment point.

Instead, the projection should be decomposed into two distinct stages:

1. **Geometric embedding**, done once.
2. **Numerical projection**, repeated cheaply.

---

## 6. Axon Embedding in the FEM Mesh

For each axonal compartment point `x_p`, find the FEM cell that contains it and compute interpolation weights.

For first-order tetrahedral elements, each point depends on four FEM nodes:

```text
x_p belongs to tetrahedron with nodes [i0, i1, i2, i3]
```

The potential at that point is:

```math
V_e[p] = w_0 φ[i_0] + w_1 φ[i_1] + w_2 φ[i_2] + w_3 φ[i_3]
```

where `w_j` are the barycentric coordinates of the point in the tetrahedron.

The package should store:

```text
node_ids[p, :] = [i0, i1, i2, i3]
weights[p, :]  = [w0, w1, w2, w3]
```

This object is the **axon embedding**.

A compact data representation is:

```text
node_ids: int32[n_points, 4]
weights:  float32[n_points, 4]
```

For first-order tetrahedral FEM, this requires approximately:

```text
node_ids:  4 × 4 bytes = 16 bytes per point
weights:   4 × 4 bytes = 16 bytes per point
total:                    32 bytes per point
```

Approximate memory requirements:

```text
1 million axonal points   ≈ 32 MB
10 million axonal points  ≈ 320 MB
50 million axonal points  ≈ 1.6 GB
```

This is often manageable, especially with chunking.

---

## 7. Projection as a Sparse Operator

The projection can be viewed as a sparse linear operator:

```math
V_e = P φ
```

where:

- `φ` is the FEM nodal potential vector,
- `V_e` is the extracellular potential at axonal compartments,
- `P` is a sparse interpolation matrix.

For P1 tetrahedral elements, `P` has exactly four non-zero values per axonal point.

However, instead of storing a general CSR sparse matrix, it is often better to store the structured representation:

```text
node_ids: int32[n_points, 4]
weights:  float32[n_points, 4]
```

This representation is:

- smaller than a generic sparse matrix,
- easier to transfer to GPU,
- simple to use in custom kernels,
- well matched to the known FEM interpolation pattern.

Given a nodal field basis:

```text
phi_basis: float32[n_contacts, n_nodes]
```

the projected axonal basis can be computed as:

```python
# phi_basis: (n_contacts, n_nodes)
# node_ids:  (n_points, 4)
# weights:   (n_points, 4)

Ve_basis = (phi_basis[:, node_ids] * weights[None, :, :]).sum(axis=-1)

# Ve_basis.shape == (n_contacts, n_points)
```

If points are grouped by axon, `n_points` can be mapped back to:

```text
n_axons × n_compartments
```

or handled using an offset-based ragged representation.

---

## 8. Avoiding Repeated CPU-GPU Transfers

A major anti-pattern is:

```text
CPU FEM field
    -> CPU projection
    -> large projected V_e array
    -> transfer V_e to GPU
    -> solve axons
repeat for every stimulation condition
```

Instead, the recommended workflow is:

```text
CPU FEM field basis
    -> transfer phi_basis to GPU once

Axon embedding
    -> transfer node_ids and weights to GPU once

GPU projection
    -> compute projected V_e on GPU by chunk or on demand

GPU axon solver
    -> consume projected field directly
```

The key objects transferred to GPU are:

```text
phi_basis_gpu:  float32[n_contacts, n_nodes]
node_ids_gpu:   int32[n_points, 4]
weights_gpu:    float32[n_points, 4]
```

These transfers happen once per FEM configuration and once per axon population, not once per amplitude, waveform, or pulse width.

---

## 9. Large Population Strategy

For small and medium populations, it may be practical to precompute and store the full projected basis:

```text
Ve_basis: float32[n_contacts, n_axons, n_compartments]
```

However, for large populations this can become too large.

Example:

```text
n_contacts     = 16
n_axons        = 1,000,000
n_compartments = 200
dtype          = float32
```

Memory requirement:

```text
16 × 1,000,000 × 200 × 4 bytes = 12.8 GB
```

This is only the projected extracellular basis, not the full state of the axon solver.

Therefore, the package should support multiple projection modes.

---

## 10. Projection Modes

### 10.1 Full Precompute Mode

Use when the population is small enough.

```text
FEM nodal basis
    -> project all axonal points
    -> store full Ve_basis
    -> run many axon simulations
```

Advantages:

- Fast repeated simulations.
- Simple implementation.
- Useful for parameter sweeps when memory allows.

Disadvantages:

- High memory footprint.
- May not scale to very large populations.

---

### 10.2 Chunked Projection Mode

Use when the full projected field does not fit comfortably in GPU memory.

```text
for each axon chunk:
    project FEM field basis onto this chunk
    solve axon dynamics for this chunk
    store compact outputs
    discard projected field for this chunk
```

The outputs should usually be compact:

```text
thresholds
activation flags
spike times
recruitment labels
summary statistics
```

rather than storing full voltage traces for every axon unless explicitly required.

Advantages:

- Scales to large populations.
- Keeps GPU memory bounded.
- Allows reuse of the same FEM field basis and embedding.

Disadvantages:

- Slightly more complex scheduling.
- Some recomputation if the same chunk is simulated many times.

---

### 10.3 Fused Projection-Solver Mode

For very large populations, the best approach may be to avoid materializing `Ve_basis` altogether.

Instead, the axon solver receives:

```text
phi_basis_gpu
node_ids_gpu
weights_gpu
contact_weights_t_gpu
```

and computes the extracellular potential directly inside the axon update kernel.

Conceptually:

```text
for each axonal compartment p:
    for each active contact k:
        Ve_k[p] = Σ_j weights[p, j] * phi_basis[k, node_ids[p, j]]

    Ve[p, t] = Σ_k a_k(t) * Ve_k[p]

    update membrane equations
```

Advantages:

- Lowest memory footprint.
- Avoids storing large projected arrays.
- Best for extremely large populations.

Disadvantages:

- More complex kernel implementation.
- More coupling between projection and axon solver.
- May require careful optimization for memory access patterns.

---

## 11. Automatic Mode Selection

The package can estimate whether full precomputation is feasible:

```python
estimated_Ve_bytes = (
    n_contacts
    * n_axons
    * n_compartments
    * bytes_per_float
)

if estimated_Ve_bytes < 0.25 * gpu_memory_bytes:
    mode = "precompute_full"
elif estimated_Ve_bytes < 2.0 * gpu_memory_bytes:
    mode = "chunked_projection"
else:
    mode = "fused_projection_solver"
```

This heuristic is intentionally conservative. The actual memory budget must also include:

- axon state variables,
- stimulus arrays,
- solver temporary buffers,
- spike/event outputs,
- GPU framework overhead,
- and possible duplicated arrays.

## 12. Recommended Data Model

### 12.1 FEMResult

```python
class FEMResult:
    mesh_id: str
    units: dict
    node_coordinates: Array
    phi_basis: Array  # shape: (n_contacts, n_nodes)
    contact_names: list[str]
    normalization: str
    reference: str
    metadata: dict
```

Purpose:

- Stores nodal extracellular potential fields.
- Represents a reusable electrode-to-volume transfer basis.
- Can remain on CPU or be transferred to GPU.

---

### 12.2 AxonPopulation

```python
class AxonPopulation:
    points: Array
    axon_offsets: Array
    axon_metadata: dict
```

Purpose:

- Stores axonal compartment coordinates.
- Supports fixed-length or variable-length axons.
- Provides mapping from flat point index to axon and compartment.

---

### 12.3 AxonEmbedding

```python
class AxonEmbedding:
    node_ids: Array   # int32, shape: (n_points, n_basis_nodes_per_point)
    weights: Array    # float32, same shape as node_ids
    point_mask: Array
    axon_offsets: Array
    metadata: dict
```

Purpose:

- Stores the geometric relationship between axonal compartments and the FEM mesh.
- Avoids repeated point-location.
- Can be cached on disk and transferred to GPU.

For P1 tetrahedral elements:

```text
n_basis_nodes_per_point = 4
```

For other elements:

```text
P1 triangle: 3
P1 tetrahedron: 4
P2 tetrahedron: 10
hexahedral Q1: 8
```

---

### 12.4 ProjectedField

```python
class ProjectedField:
    Ve_basis: Array
    layout: str
    contact_names: list[str]
    axon_offsets: Array
    metadata: dict
```

Purpose:

- Optional materialized projected field.
- Useful for small/medium populations or repeated sweeps.

---

### 12.5 ExtracellularFieldProvider

A more flexible design is to hide the projection strategy behind an interface:

```python
class ExtracellularFieldProvider:
    def get_chunk(self, axon_slice, contact_weights=None):
        ...

    def evaluate(self, point_indices, contact_weights=None):
        ...
```

Possible implementations:

```text
PrecomputedProjectedFieldProvider
ChunkedGPUProjectionProvider
FusedProjectionFieldProvider
```

This allows the axon solver to consume extracellular fields without hard-coding whether the field was precomputed, chunked, or computed on the fly.

## 13. Suggested Public API

A possible user-facing API:

```python
model = FEMModel(mesh, materials, electrodes, boundary_conditions)

field_basis = model.solve_basis(
    contacts=["E1", "E2", "E3", "E4"],
    normalization="1mA",
)

axons = AxonPopulation.from_trajectories(...)
embedding = model.build_axon_embedding(axons)

field_provider = ExtracellularFieldProvider.from_fem_basis(
    field_basis=field_basis,
    embedding=embedding,
    device="cuda",
    mode="auto",
)

stimulus = Stimulus(
    waveform="biphasic",
    amplitude=2.0,
    amplitude_unit="mA",
    pulse_width=200e-6,
)

result = AxonSolverGPU.solve_population(
    extracellular=field_provider,
    stimulus=stimulus,
    axon_parameters=params,
)
```

## 14. Caching Strategy

There are two important caches:

### 14.1 FEM Field Cache

Stores:

```text
mesh + materials + electrode configuration -> phi_basis
```

This avoids repeated FEM solves.

### 14.2 Axon Embedding Cache

Stores:

```text
mesh + axon geometry -> node_ids + weights
```

This avoids repeated point-location.

The embedding cache is especially important because point-location in an unstructured FEM mesh can be much more expensive than the subsequent interpolation.

A robust cache key should include:

```text
mesh hash
mesh coordinate system
element type
axon coordinates hash
axon coordinate system
interpolation order
tolerance
package version
```

## 15. Handling Points Outside the Mesh

Some axonal points may fall outside the FEM domain because of numerical tolerance, mesh boundaries, or geometry mismatch.

The embedding stage should explicitly handle this.

Recommended behavior:

```text
point_status[p] =
    inside
    outside
    on_boundary
    clipped
    extrapolated
```

Possible policies:

```text
strict:
    raise an error if any point is outside

mask:
    mark outside points and ignore affected axons

nearest:
    project to nearest valid cell or boundary

extrapolate:
    allow limited extrapolation within a tolerance
```

For scientific reproducibility, the chosen policy should be stored in the metadata.

## 16. Numerical and Physical Validation

Important validation checks include:

### 16.1 FEM-Level Checks

- Verify current conservation.
- Verify that the total injected current matches the total return current.
- Verify that the potential reference is well defined.
- Check mesh convergence near electrodes.
- Check sensitivity to boundary placement.
- Validate isotropic and anisotropic conductivity cases separately.

### 16.2 Projection-Level Checks

- Compare projected values against direct FEM interpolation for a random sample of points.
- Check continuity of `V_e` along axons.
- Check sensitivity to compartment spacing.
- Validate points near material interfaces and electrode boundaries.
- Ensure units are preserved.

### 16.3 Axon-Level Checks

- Validate sign convention for extracellular stimulation.
- Compare simple cases against analytical or reference solutions.
- Verify convergence with respect to time step.
- Verify convergence with respect to compartment length.
- Test known activation threshold behavior.

---

## 17. Unit and Sign Conventions

The package should be strict about units.

Common pitfalls:

```text
V versus mV
m versus mm versus µm
A versus mA versus µA
S/m versus mS/mm
extracellular potential sign convention
current-controlled versus voltage-controlled stimulation
```

For example, in many cable formulations the transmembrane potential is:

```math
V_m = V_i - V_e
```

A positive extracellular potential can hyperpolarize or depolarize depending on spatial gradients and the model convention. The package should make this explicit and test it.

Recommended metadata fields:

```text
potential_unit
length_unit
current_unit
conductivity_unit
time_unit
extracellular_sign_convention
stimulation_normalization
```

---

## 18. Memory Layout Recommendations

For GPU efficiency, use flat contiguous arrays where possible.

Recommended flat layout:

```text
all axonal compartments are flattened into one dimension

point_index = global compartment index

node_ids[point_index, 4]
weights[point_index, 4]
axon_offsets[axon_id]
```

This layout supports:

- variable-length axons,
- chunking by global point range,
- chunking by axon range,
- efficient memory transfer,
- compact indexing.

For fixed-length axons, a reshaped view may be provided:

```text
Ve_basis[n_contacts, n_axons, n_compartments]
```

but the underlying storage can remain flat.

## 19. GPU Projection Kernel Sketch

A simple GPU projection kernel concept:

```python
for p in parallel_over_points:
    value = 0.0

    for j in range(4):
        value += weights[p, j] * phi_nodes[node_ids[p, j]]

    Ve[p] = value
```

For multiple contacts:

```python
for k, p in parallel_over_contacts_and_points:
    value = 0.0

    for j in range(4):
        value += weights[p, j] * phi_basis[k, node_ids[p, j]]

    Ve_basis[k, p] = value
```

For time-dependent stimulation:

```python
for t, p in parallel_over_time_and_points:
    value = 0.0

    for k in active_contacts:
        projected = 0.0

        for j in range(4):
            projected += weights[p, j] * phi_basis[k, node_ids[p, j]]

        value += contact_weight[t, k] * projected

    Ve[t, p] = value
```

The fully fused version may compute `Ve` directly inside the axon solver update and avoid storing `Ve[t, p]`.

## 20. Recommended Development Roadmap

### Phase 1: Robust CPU FEM + Cached Projection

Implement:

- FEM solve basis on CPU.
- Axon point-location.
- Barycentric interpolation weights.
- Disk cache for FEM fields.
- Disk cache for axon embeddings.
- CPU projection for correctness.
- Extensive validation tests.

Goal:

```text
Correctness, reproducibility, and clean abstractions.
```

---

### Phase 2: GPU Projection

Implement:

- Transfer `phi_basis`, `node_ids`, and `weights` to GPU.
- GPU gather projection.
- Chunked projection mode.
- Automatic memory-based mode selection.
- Integration with GPU axon solver.

Goal:

```text
Large population support without requiring GPU FEM.
```

---

### Phase 3: Projection-Solver Fusion

Implement:

- Field provider interface consumed directly by the axon solver.
- Optional fused kernels that compute `V_e` on demand.
- Reduced materialization of `Ve_basis`.
- Streaming/chunking of axon populations.

Goal:

```text
Handle very large populations with bounded memory.
```

---

### Phase 4: Optional GPU FEM Backend

Consider GPU FEM only after profiling shows that FEM solves dominate total runtime.

Possible future backends:

```text
PETSc GPU-enabled solvers
DOLFINx with GPU-enabled PETSc
cuDOLFINx-like extensions
MFEM / PyMFEM GPU backends
custom domain-specific Poisson solvers
```

Goal:

```text
Accelerate workflows where geometry, conductivities, or electrode placements change frequently.
```

---

## 21. Anti-Patterns to Avoid

Avoid:

```text
running a new FEM solve for every waveform amplitude
performing point-location for every simulation
interpolating axons in pure Python loops
materializing huge dense projection matrices
transferring projected V_e from CPU to GPU for every run
storing full voltage traces for every axon unless needed
mixing units without explicit metadata
hiding the potential reference convention
```

Especially avoid this workflow:

```text
FEM CPU -> Python interpolation -> large NumPy V_e -> GPU transfer -> axon solve
```

inside repeated loops over amplitude, pulse width, waveform, or axon parameters.

---

## 22. Core Design Principle

The most important design idea is:

```text
The output of the FEM model should not be treated as a single 3D field.
It should be treated as a reusable electrode-to-axon transfer operator.
```

In other words:

```text
FEM field basis + axon embedding = electrode-to-axon transfer basis
```

The expensive geometric part is:

```text
axon point -> FEM cell -> FEM node indices -> interpolation weights
```

This should be computed once and cached.

After that, projecting new fields or stimulation combinations is mostly a structured sparse gather operation that can run efficiently on GPU.

---

## 23. Summary Recommendation

The recommended architecture is:

```text
CPU FEM solver with strong caching
        +
cached axon embedding in the FEM mesh
        +
GPU projection by structured gather
        +
chunked or fused GPU axon solver
```

Do not prioritize a GPU FEM solver first unless profiling clearly shows that repeated FEM solves dominate the runtime.

For large populations, prioritize:

1. Caching `node_ids` and `weights`.
2. Keeping `phi_basis` on GPU.
3. Projecting by chunks.
4. Avoiding full `Ve_basis` materialization when too large.
5. Fusing projection and axon solving for extreme-scale simulations.

This design keeps the package scientifically transparent, memory-aware, and scalable while preserving a clean path toward future GPU FEM support.
